## 🎯 Фаза 5: Адаптация по типу грунта (Sand, Snow, Dirt, Clay)

**Идея:** Roboflow возвращает теги грунта (если размечены). Использовать их для адаптации порогов.

**Реализация:**
1. В `extractPointsAndContours` (или `debug-server.js`) извлекать тег грунта из `predictions`.
2. Передавать в `ModelEnhancer` как контекст (`photoInfo.groundType`).
3. Адаптировать пороги:
   - `sand` / `snow` → `medianError` 30px → 40px, радиус слияния 5px → 8px.
   - `clay` / `asphalt` → строгие пороги (5px / 30px).
4. **Пока не реализовывать.** Сначала накопить статистику (на песке medianError = X, на глине = Y).

### 📊 Оценка
- **Приоритет: средний.** Логичная следующая фаза — порог-адаптация по типу грунта напрямую улучшает грязные следы.
- **Риск: низкий.** Изменяются только пороги (местами уже параметризованы), матчинг не трогается.
- **Зависимости:** нужно понять, отдаёт ли Roboflow тег грунта в `predictions` (проверить на реальном датасете). Если тега нет — идея превращается в «ручной выбор типа грунта в debug-UI» (можно добавить селектор).
- **Нюанс:** с переходом guard на «консенсус ≥5 пар ≤10px» порог `medianError` больше не является главным фильтром — адаптацию стоит применять к радиусу inlier (10px → 15px на песке) и радиусу слияния (5px → 8px). Это проще и честнее, чем менять medianError.

## 🎯 Фаза 6: Многомасштабный анализ (Blurred Model)

**Идея:** На грязном/снежном следе крупные детали сохраняются, мелкие — нет.

**Реализация:**
1. При создании модели помечать треугольники как `large` (площадь > 50px²) или `small`.
2. Если тег грунта `sand`/`snow` — использовать **только `large`** треугольники для первичного матчинга.
3. Если совпало — `same_footprint`. Потом добавлять мелкие детали.
4. **Пока не реализовывать.** Сначала RANSAC и треугольники.

### 📊 Оценка
- **Приоритет: высокий.** Это ровно тот механизм, который не хватало грязному отпечатку: крупные детали узнаются, мелкие не мешают. По сути — «грубая фаза» матчинга.
- **Риск: средний.** Требует пометки треугольников по площади + фильтра в TriangleMatcher — математика матчинга.
- **Зависимости:** завершить текущий консенсус (готов), собрать статистику, какой размер «крупный» на реальных следах.
- **Нюанс:** площадь треугольника зависит от масштаба фото — пометка должна быть относительной (по медиане площадей фото), а не абсолютной 50px². Иначе «large» на близком снимке ≠ «large» на дальнем.

## 🎯 Фаза 7: Краудсорсинг базы эталонов

**Идея:** Пользователи сами пополняют базу чистыми подошвами.

**Реализация:**
1. Когда приходит фото, проверять: если Roboflow не нашёл `ground`-тегов и контур замкнут — это потенциальный эталон.
2. Бот спрашивает: «Это подошва? Хотите добавить в базу? Укажите марку, модель, размер».
3. **Проверка качества:** средняя уверенность протекторов > 0.7, количество > 20. Иначе — отказ.
4. Сохранять в `data/base/raw/` с метаданными.
5. **Пока не реализовывать.** Сначала базовая архитектура.

### 📊 Оценка
- **Приоритет: средний.** Полезно для накопления данных, но требует UI/бота и процесса модерации.
- **Риск: средний.** Качество краудсорсинга неконтролируемо; критерии >0.7 и >20 — разумный минимум, но нужна статистика отказов.
- **Зависимости:** функция «сохранить эталон» (фото + метаданные, без графа — см. Фазу 8), формат хранения.
- **Нюанс:** хранить ТОЛЬКО фото + метаданные (без графа) — граф строится на лету (это уже описано в Фазе 8 и это правильное решение: граф зависит от версии детекции).

## 🎯 Фаза 8: Версионирование детекции и миграция

**Идея:** Если Roboflow улучшится, старые модели устареют.

**Реализация:**
1. В модель добавлять `detectorVersion` (например, `"roboflow-v1"`).
2. **Исходные фото хранить всегда** (в `data/base/raw/`). Без них миграция невозможна.
3. **Эталоны хранить как фото + метаданные, без графа.** Граф строится на лету при поиске.
4. При обновлении детекции — пересобирать графы в фоне (не блокировать работу).
5. **Пока не реализовывать.**

### 📊 Оценка
- **Приоритет: высокий (архитектурный).** Это фундамент для Фаз 5–7 и для доверия к результатам.
- **Риск: низкий по коду, средний по объёму** — затрагивает модель данных (метаданные) и процесс поиска (граф на лету).
- **Зависимости:** хранилище исходников + метаданных; это базовая инфраструктура, которую стоит заложить ДО краудсорсинга (Фаза 7).
- **Нюанс:** «граф на лету» увеличивает время поиска — стоит добавить кэш собранных графов по `(photoHash, detectorVersion)`, чтобы не пересобирать часто используемые эталоны.

## 🎯 Фаза 9: Динамический анализ (Dragged)

**Идея:** Выволока (`Dragged`) — это мета-признак деформации (человек двигался, грунт вязкий).

**Реализация:**
1. При извлечении точек: если точка в зоне `Dragged`, помечать `isDynamic: true`.
2. При матчинге: для `isDynamic` точек увеличить порог inlier (10px → 20px).
3. При слиянии: для динамических точек использовать более сильное усреднение (70/30 в пользу модели).
4. **Пока не реализовывать.**

### 📊 Оценка
- **Приоритет: низкий (после Фаз 5–6).** Сейчас `Dragged` — контур (не точка, мы это уже исправили); использование его как зоны-метки — отдельная фича.
- **Риск: низкий.** Пометка точек по попаданию в полигон `Dragged` — простая геометрия.
- **Зависимости:** Фаза 5 (контекст грунта) — вместе они образуют «адаптивный матчинг по условиям съёмки».
- **Нюанс:** увеличение inlier-радиуса для динамических точек может пропускать ложные пары — порог 20px стоит проверять на реальных следах с выволокой.

## 🎯 Фаза 10: Дополнительные улучшения (из обсуждения)

1. **Кэш Spatial Hash** для быстрого поиска (разбить модель на сетку 50x50px).
2. **Confidence Heatmap** на визуализации (зелёный = 10+ подтверждений, красный = 2).
3. **Автоматический выбор лучшего фото** для фона супер-модели (по качеству детекции).
4. **Разбиение модели на зоны** (Palm/Toe/Heel) с использованием классов Roboflow.
5. **Генерация синтетических деформаций** для калибровки порогов.
6. **Использование контура** (`Outline-trail`) как ограничителя (отсев пар, выходящих за контур).

### 📊 Оценка
- **Spatial Hash:** приоритет средний — пригодится, когда база эталонов вырастет (Фазы 7–8). Сейчас наборы маленькие, оверхед не нужен.
- **Confidence Heatmap:** приоритет низкий — косметика debug-UI, дёшево сделать, но не влияет на результат.
- **Автовыбор фона супер-модели:** приоритет средний — визуально важно, когда фото разного качества; дёшево (по средней уверенности детекции шага).
- **Зоны Palm/Toe/Heel:** приоритет высокий для будущего (аналогично Фазе 5: зональные пороги), но требует стабильных классов от Roboflow.
- **Синтетические деформации:** приоритет средний — лучший способ калибровать пороги inlier/слияния без полевых данных; сделать можно после Фаз 5–6.
- **Контур как ограничитель:** приоритет **высокий и самый дешёвый** — отсев пар, чья проекция выходит за контур следа, вероятно сразу уберёт часть ложных якорей. Проверить на текущих логах.
